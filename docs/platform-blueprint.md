# 游戏平台设计方案（PC + Android）

> 定位：轻量级客户端 + 内容社区 + 自助发行后台。视觉走二次元/高动效风格。
> 文档目标：给出可落地的功能地图、关键机制与技术架构，而不是堆概念。

---

## 0. 一句话定位与差异化

"又一个 Steam" 是必死路线。可选的差异化切口：

| 切口 | 说明 | 适配度 |
|---|---|---|
| 垂直品类 | 只做二次元 / 独立 / Galgame / 同人 / 肉鸽 | 高，冷启动容易 |
| 轻量启动器 | 100MB 以内、秒开、游戏库聚合（含非平台游戏导入） | 高，技术差异点明确 |
| 社区优先 | 动态/评测/车队为核心，商店是附属 | 中，需内容运营能力 |
| 云试玩 | 点开即玩 10 分钟，再决定下载 20GB | 中，带宽成本高 |
| 自助发行 | 小团队 30 分钟上架，分成透明 | 高，供给端好切入 |

建议：**垂直品类 + 轻量启动器 + 自助发行**。供给端先自研/独代 3~5 款兜底，避免双边市场冷启动死锁。

## 1. 功能地图（按优先级分层）

### P0 — 没有它就不算平台

**客户端基础**
- 账号体系：手机/邮箱注册、第三方登录（微信/QQ/Google/Apple/Steam）、设备绑定、多端登录管理
- 游戏库：已安装/未安装/收藏/分组/标签、本地已安装游戏扫描与手动导入、游玩时长统计
- 安装与更新：一键安装、断点续传、多线程分片下载、限速、校验与"修复文件"、安装路径/磁盘空间预检
- 启动：进程启动与退出监听、单实例锁、协议唤起 `platform://launch?appid=`
- 客户端自更新：差分升级、静默更新、失败回滚

**商店与发现**
- 游戏详情页：截图/视频/配置要求/标签/评测摘要
- 列表与筛选：分类、标签、价格、平台、语言
- 新游推荐位 + 编辑精选 + 排行榜（热销/新品/好评）
- 搜索（中文分词 + 拼音/别名容错）

**发布后台（开发者）**
- 构建上传（分片上传 + 秒传）、多平台产物矩阵（Win x64 / Android arm64 / Android x86_64）
- 版本通道（正式 / 测试 / PTR）、审核流、定时发布、一键回滚
- 商店页装修：图文素材、多语言、分级

**运营后台**
- 首页楼层/横幅/推荐位可视化配置
- 用户/订单/内容审核管理
- 基础数据看板（下载、安装、DAU、留存）

### P1 — 决定留存的"实际有效"功能

1. **内容寻址增量更新**（见 §2.1）—— 直接决定带宽成本和更新体验，比任何花哨功能都重要
2. **云存档同步** + 冲突解决 UI（时间戳 + 手动选择覆盖）
3. **预下载 + 定时解锁**：发售前下完，到点自动可玩；新版本后台静默更新
4. **愿望单 + 降价/发售/好友动态提醒**（站内信 + 系统推送，Android 需接厂商通道）
5. **评测系统**：必须带"是否拥有/游玩时长"权重，否则必被刷；短评 + 标签化评价（"剧情好/优化差"）
6. **成就系统 + 平台等级/徽章**：跨游戏统一的成长体系，成本低、粘性高
7. **好友在线状态 + 邀请加入（Rich Presence）**：显示"正在玩 XX / 在菜单中"，一键组队
8. **文件完整性校验与修复**：玩家最高频的求助场景，做好能砍掉一半客服工单
9. **崩溃与日志上报**（Crashpad/Sentry + 符号表管理）：没有它你永远在盲修
10. **工单/客服 + 常见问题 + 申诉通道**

### P2 — 商业化与生态

11. **支付与订单**：支付宝/微信/Stripe、优惠券、捆绑包、限时折扣、退款策略、防欺诈风控
12. **兑换码/激活码**、充值卡、礼物赠送
13. **开发者分成与结算**：对账、发票、提现、退款冲正（这块工作量常被严重低估）
14. **创意工坊 / Mod 管理**：依赖解析、冲突检测、一键启用订阅。对单机/二次元游戏是留存核弹
15. **动态 Feed + 关注开发者 + 专题合集**（UGC 内容区）
16. **创作者中心**：投稿攻略/视频，按播放分成
17. **P2P / 多源分发**（见 §2.1）
18. **云游戏/云试玩**（独立子系统，成本高，放最后）

### P3 — 差异化与增值

19. **手柄全流程导航 + 大屏/客厅模式**（掌机、电视、Steam Deck 类设备）
20. **悬浮窗 Overlay**（PC：好友/语音/截图/FPS）
21. **多版本共存与降级**（玩家常因 MOD 兼容回退旧版本）
22. **家庭共享 / 多账号切换**
23. **离线模式与弱网重试策略**
24. **Android 免安装试玩**（Instant Play / 云试玩）
25. **A/B 实验平台**（推荐位、定价、文案）
26. **成就/时长导入 Steam**（迁移工具，抢用户很有效）

### 合规（不是功能，是门槛）
- 实名认证 + 防沉迷时长/消费限额、年龄分级、隐私政策与权限清单
- 内容审核（机审：ClamAV/VirusTotal 病毒扫描 + 人审 + 举报闭环）
- 数据合规：个保法/GDPR、数据出境、日志留存
- **Android 分发现实**：Google Play 的数字内容内购强制走 Play Billing；国内需版号与各渠道联运。较现实的路径是「启动器 + 社区 + 资源分发」，内购交由游戏自有支付或官方渠道，或先做海外/自助发行市场。此点需法务确认，不要等到上线前才发现。
  > 2026-10 决策：主战场为 PC、目标海外，Android 降级为 P2 阶段（先做"社区 + 启动器"，不做 APK 商店）。

## 2. 关键机制设计

### 2.1 更新系统：内容寻址（CAS）而非"版本对补丁"

传统做法是每两个版本之间生成 bsdiff 补丁，版本一多就是 N² 爆炸。正确做法是内容寻址存储：

```
文件 → 按内容切块（FastCDC，平均 1 MiB）→ 每块算 sha256 → 全局块索引
```

Manifest（服务端生成、Ed25519 签名）：
```json
{
  "app_id": "100234",
  "build_id": "b_20261024_1",
  "platform": "windows-x86_64",
  "version": "1.4.2",
  "total_size": 21474836480,
  "files": [
    { "path": "Game.exe", "size": 123456, "exec": true,
      "chunks": ["sha256:9f2c...", "sha256:1a7b..."] }
  ],
  "chunks": { "sha256:9f2c...": { "size": 1048576, "url": "/cas/9f/2c" } },
  "signature": "ed25519:..."
}
```

更新流程：
1. 拉 manifest（带 If-None-Match，未变则 304）
2. 与本地 manifest 求差集 → 只下载缺失块
3. 每块下载后校验 sha256，落盘到 `~/.platform/cas/`
4. 按 chunk 列表拼装文件（优先 hardlink/reflink），原子替换，保留旧版本用于回滚
5. 失败可断点续传（chunk 级），不重下整个文件

收益：
- **任意版本间增量，服务端零额外计算**，不需要预先算补丁
- 改一个 100MB 的资源包，只下变化的几 MB
- 天然支持"边下边玩"：按优先级先下启动必需文件
- 卸载可保留 CAS，重装秒装；用引用计数做 GC

**Android 特殊点**：APK 本身签名后不可打补丁，整包更新；增量只作用于资源包/obb。或者用 Play Asset Delivery / 自有资源分包方案。
**启动器自更新**：单体可执行文件，用 zstd/bsdiff 差分 + Tauri updater 的签名校验。

### 2.2 分发与成本（这是最大的运营成本）

一个 20GB 游戏下载 1 万次 = 200TB。必须做的三件事：
- **CDN 多源 + 客户端测速选源**，按地区/运营商调度，失败自动切换
- **增量更新**（§2.1）：把平均下载量降一个数量级
- **P2P 辅助**（PC 可选项，WebRTC/libtorrent）：省 30%~50% 带宽，注意做上传限速与"只对同版本做种"

### 2.3 发布流水线

```
开发者上传构建 → 秒传/分片上传 → 服务端切块入库(CAS) → 生成 manifest + 签名
→ 病毒扫描/机审 → 人审 → 灰度(按 user_id 哈希分桶) → 全量 → 指针切换(秒级回滚)
```

灰度与回滚都是"manifest 指针切换"，不要做重新构建。

### 2.4 安全红线

- **manifest 必须签名，客户端内置公钥**；否则 CDN 或中间人可注入任意文件 → 全量 RCE
- 每个 chunk 校验 sha256，拼装后再校验整文件
- 客户端永远不可信：拥有关系、订单、成就、时长以服务端为准
- 下载接口做签名 URL + 防盗链 + 频率限制；防刷 CDN
- Windows 代码签名证书（EV）——不做的话杀软误杀会让你丢掉一半用户
- 启动器提权：安装到 Program Files 才需要 UAC，默认装用户目录可避免

## 3. 技术架构

### 3.1 总览

```
┌─────────────── 客户端（一套代码，双端） ───────────────┐
│ UI 层         React + TS + Tailwind + framer-motion     │
│              动效资产：Rive / Lottie / PixiJS(Particle) │
│ 状态层        TanStack Query + Zustand（领域状态机）      │
│ 领域服务      install / update / launch / library / auth │
│ 平台适配      Win(进程/注册表/快捷方式)  Android(PM/前台服务)│
│ 原生内核      Rust: 下载器 / CAS / 校验 / 解压 / 自更新    │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTPS + WebSocket
┌───────────────────────────▼─────────────────────────────┐
│ 接入层   API Gateway / BFF（鉴权、限流、聚合、签名URL）     │
├──────────────────────────────────────────────────────────┤
│ 业务层（模块化单体起步，按域拆包，热点再拆服务）             │
│  account · catalog · build/manifest · entitlement/order   │
│  community · review · achievement · notification · admin  │
├──────────────────────────────────────────────────────────┤
│ 异步层  任务队列（切块/转码/推送/结算） · 事件总线(NATS)     │
├──────────────────────────────────────────────────────────┤
│ 数据层  PostgreSQL（事务） Redis（缓存/会话/限流）           │
│         ClickHouse（埋点/分析） Meilisearch（搜索）         │
│         对象存储 S3/OSS（构建产物、CAS、图片）              │
└───────────────────────────┬──────────────────────────────┘
                            │
                    CDN（多源 + 回源到对象存储）
```

### 3.2 为什么起步用"模块化单体"

平台早期 QPS 很低，微服务只会让你用 80% 时间维护基础设施。做法：
- 单个 Go 服务，内部按 domain 分 package，禁止跨域直连数据库
- 对外只暴露一个 BFF 聚合接口
- 把"下载/manifest 分发"和"埋点上报"这两个**天然高流量**的模块**一开始就独立部署**（它们和业务 QPS 差 3 个数量级）
- 埋点先落 Kafka/NATS → ClickHouse，不要写业务库

### 3.3 技术选型

**客户端（核心决策）**

| 方案 | 优势 | 风险 |
|---|---|---|
| **Tauri v2 + React/TS + Rust**（推荐） | 花哨 UI 成本最低；Rust 内核做下载/校验/补丁/进程管理很顺手；包体 10~30MB；PC+Android 一套 | Android WebView 碎片化，低端机 WebGL 动效掉帧 |
| Flutter | 自绘一致性好，Rive 生态成熟，双端稳 | 桌面端细节（托盘/注册表/多窗口）要自己写插件 |
| Compose Multiplatform | Kotlin 一套代码，原生性能 | 重度动效开发成本最高，生态较新 |

选 Tauri 的兜底策略：**设备性能分级**（GPU/内存探测）→ 自动降级动效（静态图/降低粒子数/关闭模糊），关键动效用 Rive 预渲染而非实时 shader。若 Android 是主战场且低端机占比高，改选 Flutter 更稳。

**服务端**：Go（高并发下载/网关友好）或 Kotlin/Spring（团队是 Java 背景）。PostgreSQL 必选；缓存 Redis；搜索 Meilisearch（比 ES 省事）；分析 ClickHouse（可晚点再上，先用 PG 物化视图）。

**部署**：起步 Docker Compose + 托管 PG/Redis + 对象存储 + CDN，2 台机器够用；上量再迁 K8s。可观测性从第一天就接 OpenTelemetry + Sentry。

### 3.4 核心数据模型

```
users(id, ...)            devices(id, user_id, fingerprint, os)
games(id, slug, title, status, rating_age, developer_id)
game_localizations(game_id, locale, name, description, ...)
builds(id, game_id, platform, version, channel, status, manifest_url, signature)
build_chunks(build_id, chunk_hash, size)      -- 或只存 manifest 指针
manifests(id, build_id, hash, signature, size, created_at)
entitlements(user_id, game_id, source, acquired_at)   -- 拥有权，一切权限的根
orders(id, user_id, amount, currency, status, channel)
library_items(user_id, game_id, install_path, installed_build_id, playtime_sec)
reviews(user_id, game_id, rating, body, playtime_sec, helpful_count, status)
wishlists / follows / achievements / user_achievements
saves(user_id, game_id, slot, blob_url, hash, updated_at)   -- 云存档，冲突靠 updated_at+hash
telemetry_events → ClickHouse
```

关键点：**entitlement 表是所有权限的唯一事实来源**，下载签名 URL、云存档、评测资格都从它派生。

### 3.5 客户端内部分层原则

- 下载/安装/更新必须是**可恢复的状态机**，落盘持久化（断电、崩溃、杀进程后能续），不要用内存标志位
- 所有网络请求走统一 SDK（重试、退避、超时、离线队列）
- UI 与内核通过命令/事件通信，UI 崩溃不能影响下载
- 埋点统一 schema（event_name + props），别让每个页面自己拼字段

## 5. 风险清单

| 风险 | 应对 |
|---|---|
| CDN 带宽成本失控 | 增量更新 + P2P + 多源调度 + 下载限速/排队 |
| Android 渠道与合规 | 早期只做海外或 PC 主战场，Android 定位"社区+启动器" |
| 内容供给不足（冷启动） | 自研/独代兜底 3~5 款，先做工具属性（游戏库聚合）拉人 |
| 客户端被篡改/破解 | manifest 签名、服务端权威校验、关键逻辑不落客户端 |
| 杀软误报 | EV 代码签名、白名单报备、安装包体积与行为规范 |
| 二次元美术产能不足 | 组件化 + Rive 模板 + 动效分级降级 |
| 微服务过度设计拖慢进度 | 模块化单体，只拆下载与埋点 |

## 6. 已锁定决策（2026-10）

> 输入：PC 主战场、目标海外、前期自研为主、后续开放第三方接入。
> 下面的内容**覆盖**前文与之冲突的部分。

### 6.1 平台范围

| 项 | 决策 | 影响 |
|---|---|---|
| 首发平台 | Windows 10/11 x64 | WebView2 系统自带，安装器最小；macOS/Linux 放 P2 |
| 安装位置 | 默认 `%LOCALAPPDATA%`，可选其他盘 | **避免默认 UAC 提权**，减少一半安装失败 |
| 代码签名 | EV 证书从第一天就买 | 不签 = 杀软误杀 + SmartScreen 拦截，直接丢用户 |
| 启动器体积 | < 40 MB | 首次安装转化率的关键指标 |
| Android | P2，定位"社区 + 库 + 启动器" | 不做 APK 商店，规避 Play 政策与渠道问题 |

### 6.2 海外市场

| 项 | 决策 | 注意 |
|---|---|---|
| 支付 | Stripe（卡 + Apple/Google Pay）+ PayPal | 中国大陆主体接 Stripe 需境外实体，提前 2 个月办 |
| 定价 | 美元基准 + 区域定价（购买力平价） | 土耳其/阿根廷/俄区必须单独定价，否则被套利 |
| 分级 | IARC 问卷（一次问卷覆盖 ESRB/PEGI/USK/CERO） | 比逐个申请便宜且快 |
| 合规 | GDPR / UK GDPR / CCPA + 年龄门禁 | 埋点必须能做"拒绝即不采集"，别事后补 |
| 语言 | en-US 首发，zh-CN / ja-JP 第二梯队 | 二次元品类日文优先级高于其他语种 |
| 内容政策 | 明确禁止清单 + 举报流程 + DMCA 代理 | 三方接入后这是必需品，不是奢侈品 |
| 税务 | 三方开发者结算需 W-8BEN / W-9 | 否则无法合规打款 |

### 6.3 内容策略：先自研，后开放

三方接入不能一上来就"注册即上架"，否则审核与盗版会直接拖垮小团队。建议三段式：

1. **自研期（M1–M3）**：只上自家 2~3 款，把发布流水线、更新、支付、客服跑顺
2. **邀请制（M4）**：白名单开发者，人工审核 + 合同 + 分成（建议 85/15 ~ 70/30）
3. **开放期（M5+）**：自助注册，但保留"上架前人工审核 + 病毒扫描 + 运行时抽检"，
   并设置保证金/下架条款

开放期的三个硬性前提：
- **机器审核流水线**：ClamAV + 多引擎扫描 + 敏感文件检查（签名证书、注入行为）
- **可回滚发布**：不良版本必须能在 5 分钟内全量下架（manifest 指针置空）
- **结算系统**：对账、退款冲正、提现、发票，至少提前一个季度做

  否则冷启动数据量根本喂不动机型
